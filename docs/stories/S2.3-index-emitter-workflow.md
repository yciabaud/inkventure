## User story

As a Kindle user, I want a compact catalogue that loads quickly so that browsing the library is fast.

## Scope

- Emit `public/catalog/meta.json`, `index-<n>.json` (short keys, ~500 rows), `games/<tuid>.json`.
- Validation: JSON schema, shard size < 150 KB, drop > 20 % vs previous build fails.
- Scheduled weekly GitHub Action + manual dispatch; publishes the data with the Pages build (data branch or artifact).
- Small committed sample catalogue for dev/e2e.

## Acceptance criteria

- [x] Weekly workflow produces and deploys a valid index; the app build picks it up. _(verified locally and by simulation; first real run after merge, see Notes)_
- [x] Sample catalogue available for local dev and tests.

## Notes & decisions

- **Code**: `scripts/catalog/emitter.ts` (pure: rows, shards, facets, validation), `emit.ts` (CLI,
  `npm run catalog:emit`), `files.ts` (writing), `sample.ts` + `build-sample.ts` (`npm run catalog:sample`),
  `use-published.sh`; workflow `.github/workflows/catalog.yml`. Format and usage in `scripts/catalog/README.md`.
- **Data branch**: the weekly run commits the catalogue, the crawler's record cache (so the next crawl is
  incremental) and `report.json` to the `catalog` branch (created on the first run with an orphan worktree), then the
  deployment (now also triggered by `workflow_run` of Catalogue) copies `catalog/` into `public/catalog/` before
  building. Chosen over artifacts, which expire and cannot be read back by the next run. Preview builds use it too.
- **Drop check** against the `meta.json` on the branch; the first run has none. **Schema** checks are hand-written
  (no JSON-schema dependency). Files are written compact (no indentation).
- **Size check** (`check:size`): index shards and `meta.json` one row each; the thousands of game details are checked
  through their largest one.
- **Sample** (`public/catalog/`): the 11 synthetic fixture games through the whole pipeline, 4 kept (Z-code). Enough
  to load; S3.1 may need a larger synthetic set for paging and filters. A unit test fails when it is stale.
- **Not done**: `fg` (forgiveness) stays empty (IFDB's JSON API lacks it, S2.2); file sizes are unknown.
- **First real run**: after merge, run **Catalogue** from the Actions tab (or wait for Monday). The first crawl fetches
  every record at 1 request/s (the job allows 5 hours); it creates the `catalog` branch and triggers a deployment.
