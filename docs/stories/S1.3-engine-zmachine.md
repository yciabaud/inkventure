## User story

As a player, I want to play a Z-machine game in the reader so that the core experience works end-to-end.

## Scope

- `Engine` interface (SPEC §4.2) and `OutputBlock` model.
- GlkOte-compatible bridge translating Glk updates (buffer window, grid/status window, styles) into blocks.
- ZVM integration (from Parchment, licence checked and recorded), lazy-loaded chunk, ES5-safe.
- Bundled freely-licensed fixture Z-game in `tests/fixtures/` and served for the demo; `#/play/fixture-z` route.
- Basic line input field (full command bar is S1.4); char input via tap.

## Acceptance criteria

- [x] A full session of the fixture game can be played in the reader (commands, outputs, [MORE]/key prompts).
- [x] Legacy bundle passes es-check including the engine chunk.
- [x] Engine chunk not loaded on Home/Library.

## Required tests

**Unit (Vitest)**

- Headless adapter test: load fixture, run a scripted walkthrough, assert expected outputs; status line extraction.

**E2E (Playwright)**

- Open `#/play/fixture-z`, type `look`, see the room description on the last page.

Plus the global gates: lint, `es-check es5` on the legacy bundle, CI green.

## Out of scope

- Saves (S1.5), chips (S1.4), downloading real games (S3.4).

## Notes & decisions

- **Engine interface** (`src/engines/engine.ts`) as in SPEC §4.2, plus `onExit` and `onError`. `OutputBlock` =
  `paragraph` (styled runs with Glk style names, `append` to continue the previous one) | `status` (whole status line)
  | `clear`. `saveState` / `restoreState` / `undo` reject for now (S1.5). SPEC §4.2 updated.
- **ZVM and Glk from npm**, pinned: `ifvms` 1.1.6 (ZVM) and `glkote-term` 0.4.4 (only its `glkapi.js`), both MIT
  (recorded in `src/engines/README.md`). Their terminal front ends are not bundled. Two build-time patches
  (`scripts/build/vendor-patches.ts`, Vite plugin, also applied in Vitest by inlining the packages) make them run from
  an ES module bundle: `glkapi.js` becomes a factory (`createGlk()`: one Glk instance per game, its implicit globals
  declared; upstream it only works as a sloppy-mode singleton), and `opcodes.js` no longer reads `this` at module
  level (fine in Node, broken once converted from CommonJS: the game crashed at start in the minified build only).
  Each patch fails the build if upstream changes, and has unit tests.
- **GlkOte bridge** (`src/engines/glkote-bridge/bridge.ts`, no DOM): answers `init` with metrics of 1-px characters
  so the "screen" is `columns` wide (80: below ~66 columns Inform shortens the status line to "3/12"); turns buffer
  window lines into paragraphs and the grid window into the status line; reports line / char input requests; answers
  file prompts (save/restore) with "cancelled" until S1.5; plus an in-memory `Dialog`.
- **Transcript** (`src/engines/transcript.ts`): immutable, unchanged paragraphs are shared; `clear` is ignored (a
  paginated transcript keeps everything). `src/reader/fromTranscript.ts` drops blank lines and, while a command is
  awaited, the bare ">" prompt, and keeps one `ReaderBlock` object per paragraph.
- **Reader changes** (S1.1 code): styled runs (`reader__run--*`: italic, bold, monospace), measured across several
  text nodes; **incremental measurement** (only new blocks are measured at the same width; the S1.1 follow-up); the
  page turner opens on a `focus` block (the echoed command) when text arrives; **turns kept together** (a turn that
  does not fit the rest of the page but fits a page starts a new page, SPEC §3.6 updated), so the reply and the
  command bar are usually on the same page.
- **Game screen** (`src/screens/reader/GameReader.tsx`, `#/play/fixture-z`): the engine chunk and the story file load
  in parallel; the top zone shows the status line (location left, score / moves right); the slot under the last page
  holds a basic command field + Enter (S1.4 brings chips and history), "Continue ›" for key prompts, or "The story
  has ended."; a tap on the last page or any key also answers a key prompt. Errors show the error page. The reader
  chrome shared with the demo moved to `ReaderFrame.tsx`.
- **Fixture game**: "The Lamp at Saltmere" (`tests/fixtures/zmachine/lamp.inf` → `lamp.z5`, 88 KB), written for the
  project and compiled with Inform 6.41 + library 6.12 (compiled games may be distributed freely), rebuilt by
  `scripts/fixtures/build-z.sh`; served through a Vite `?url` import, so it is fetched only by the reader.
- **Sizes**: engine chunk ≈ 46 KiB gz (modern) / 45 KiB (legacy), budget 100. The initial legacy JS grew from 59 to
  75 KiB gz (core-js polyfills for the engine code land in the legacy polyfills chunk); the modern one from 15.5 to
  18 KiB (game screen and transcript code).
- **Tests**: unit: headless adapter (key prompt, full walkthrough to the win, command echo, status line extraction,
  unexpected input ignored, two games side by side, non-Z-code rejected), vendor patches, transcript → blocks, turns
  kept together. E2E (`zmachine.spec.ts`): `look` shows the room on the last page; a full session to the ending with
  the status line and every page fitting; key prompt by keyboard; engine chunk and story file not loaded on Home /
  Library; download failure → error page; tap targets.
- **Follow-ups**: the "▸ more" marker of SPEC §3.6 is not drawn yet ("Back to the present ›" shows on earlier pages;
  turns kept together make it rare) — S1.4 or S1.6. Turn latency on a real Kindle (SPEC §4.5 targets) is still to be
  measured (S7.1). The modern bundle has no gate against syntax the Kindle lacks (`?.`): checked by hand here, a CI
  check would be worth a small story. Status line tap → reader menu is S1.6.
