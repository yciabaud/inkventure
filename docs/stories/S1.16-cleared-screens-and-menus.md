## User story

As a player browsing a game's menu (help, hints, options), I want to see only the current menu screen, so that I
don't page through every earlier copy of it.

## Background

Found on 2026-10-01 (Bronze `HELP`, production vs Parchment). An Inform menu clears the main window and redraws
itself after each key. Parchment honours the clear: one screen, always in the same place. The reader ignores
`clear` blocks ("the paginated transcript keeps everything", SPEC §4.2), so every redraw of the menu and every
topic is **appended**. In a few key presses the page count went from 4/4 to 7/7, and after each key the reader shows
an earlier page with "Back to the present ›" to tap. It is confusing, and each extra tap costs an e-ink refresh.

## Scope

- A `clear` block starts a new screen: the reader opens the next output on a fresh page, and the text before it is
  no longer on the same page.
- **Screens with only key presses in between** (no command, no choice: a menu being browsed) replace each other
  in the paged view. When the game goes back to line input, only the last screen before it stays in the pages.
  Decide and record whether the Transcript view keeps the replaced screens.
- The reader shows the latest screen at once, with no "Back to the present" step, when the new screen fits on one
  page.
- Autosave and undo are unchanged: snapshots are still taken on line input only.
- SPEC §3.6 / §4.2 updated (`clear` no longer ignored).

## Out of scope

- Real-time or animated screens (status bars that redraw on a timer).
- Drawing the upper window as a full-screen grid.

## Notes & decisions

- **Model** (`src/engines/transcript.ts`): a `clear` block marks the next paragraph `screen` (it starts a screen) and
  counts screens. At a clear, the current screen (from the last screen start) is marked `replaced` when no command was
  echoed in it, i.e. it was reached by key presses only. The game's first screen (no clear before it) is never
  replaced. Consecutive clears count once. An `append` after a clear starts a new paragraph.
- **Replaced screens and the Transcript view:** replaced paragraphs stay in the in-memory transcript, so the Transcript
  view shows every screen of the menu, each on its own page. The game view leaves them out (`readerBlocks`), and so do
  saves and the Undo snapshot written to disk. After a reload, the Transcript view has the tail kept with the autosave,
  as before, without them.
- **Which screens are replaced:** the rule is the story's ("key presses only"), so besides menu screens, title or
  intro pages shown one after another with "press any key" and cleared are replaced too: the game view then starts at
  the screen that was on show when the first command was typed. They stay in the Transcript view.
- **Fresh page:** a block starting a screen always opens a page (`paginate(…, screenStarts)`), unless it is already at
  the top of one. A turn's grouping (command + reply on one page) stops at a screen start, so the command that opened a
  menu stays with the text before it.
- **Opening on the new screen:** the reader remembers how many screens had started when the last key, command or
  choice was sent; when a new one has started since, the pages open on the last screen start instead of the start of
  the turn. A menu screen fits on one page, so it shows at once with its key chips, without "Back to the present".
  After a reload, undo or restore, the pages open on the later of the last command and the last screen start.
- **Lost echo:** Glk drops everything the window held before a clear, including its own echo of the command, so a
  command whose reply clears the window (`HELP`) left a bare ">" (already before this story). The bridge now remembers
  the line it sent and, when the window's next update starts with a clear, emits the echo first.
- **Saves:** a snapshot also stores `screens`, the indexes of the paragraphs starting a screen, counted from the
  transcript tail it keeps; saves made before it have none and load as before (no format version change).
- **Fixture:** `lamp.inf` has a `MENU` verb drawn like the Inform library's menus (`@erase_window 0` and a three-row
  status window with the legend at each key; two topics; N / P / Return / Q), rebuilt with Inform 6.41. HELP and
  LOGBOOK, used by S1.12's tests, are unchanged.
- **Bronze** (real story file, from the IF Archive): HELP, N, N, P, Return (a submenu), a topic, Space, Q, Q: one menu
  screen at a time in the game view, and after Q the game's text, ">help", then Bronze's room description on a fresh
  page (Bronze clears the window when the menu closes, so the menu's last screen is replaced).
