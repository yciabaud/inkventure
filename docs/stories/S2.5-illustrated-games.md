## User story

As a reader, I want to find the games that come with pictures so that I can enjoy illustrated adventures on my
e-reader.

## Scope

- **Detection in the pipeline.**
  - A game is *illustrated* when its playable file is a Blorb (`.gblorb`, later `.zblorb` if an engine renders
    pictures) holding at least **two `Pict` resources besides the cover** (the frontispiece named by the `Fspc`
    chunk).
  - The resource index (`RIdx`) sits at the start of a Blorb, so read only the file's head: an HTTP `Range` request
    for the first few KB, falling back to a full download if `Range` is not honoured. Same politeness as the crawler
    (≤ 1 request/s, project `User-Agent`).
  - Cache the result per file URL (and size or `Last-Modified`) next to the crawler's record cache, so a weekly run
    only inspects new or changed files.
  - Only formats whose engine draws pictures count: Glulx once S1.10 has shipped.
- **Index.** Add `il: 1` to index rows (and `illustrated: true` plus the picture count to `games/<tuid>.json`) for
  illustrated games; add the illustrated count to `meta.json`.
- **Library.** An "Illustrated" filter, a single yes choice with its count, serialised as hash key `ill`.
- **Game detail.** An "Illustrated" badge next to the format badge.
- i18n strings in `en.json` and `fr.json`.

## Acceptance criteria

- [x] The pipeline flags illustrated Blorbs from their head only, caches the result, and reports the counts in
      `report.json`.
- [x] The Library "Illustrated" filter narrows the results and survives reload and the back button; the badge shows
      on game detail.
- [x] SPEC §3.4, §3.5 and §5.2 match the implementation.

## Required tests

**Unit (Vitest)**

- Blorb `RIdx` parser on recorded fixtures: no pictures, cover only, several pictures; a truncated head; a file that
  is not a Blorb.
- `Range` fallback and the per-URL cache (recorded responses, no network).
- Emitter writes `il` and the `meta.json` count; the filter predicate and hash serialisation of `ill`.

**E2E (Playwright)**

- With the sample catalogue (one illustrated fixture game), the "Illustrated" filter shows only that game; its detail
  page shows the badge.

Plus the global gates: lint, `es-check es5` on the legacy bundle, CI green.

## Out of scope

- Rendering the pictures in the reader (S1.10).
- A dedicated "Illustrated" shelf on Home: a follow-up once the count of illustrated games is known.
- Detecting pictures in Twine or Ink games, and new picture-based engines (Decker, see
  [post-v1-ideas.md](../post-v1-ideas.md)).
- Judging how good the pictures look in grayscale; curation can add notable ones to `featured.json`.

## Notes & decisions

- **A separate step, like the CORS check.** `check-pictures.ts` (`npm run catalog:pictures`) runs after the CORS
  check and before resolving: it resolves the raw dataset offline to know which files the catalogue will use, then
  inspects them and writes `data/cache/pictures.json`; `resolve.ts --pictures` reads it, so the resolver stays offline
  and pure. The weekly workflow keeps the cache on the `catalog` branch next to `cors.json`.
- **Head only.** A `Range` request for 4 KB; when the index is longer (more than ~330 resources) it is asked for once
  more, as long as needed (capped at 256 KB). When a host ignores `Range` (200), the response is read only until those
  bytes have arrived and then closed, rather than downloading the whole file.
- **Cover.** The `Fspc` chunk is found by walking the chunks after the index while their headers are in the head.
  When it is not there (and the walk did not reach the end of the file), one picture is assumed to be the cover:
  this can only under-count, never flag a game wrongly.
- **Cache key.** Entries are keyed by URL and store the size and `Last-Modified`. Learning those needs a request, so a
  check is reused for 90 days without asking, then revalidated with `If-Modified-Since` (a 304 keeps the count; a
  changed file is inspected again). Network errors and 5xx answers are checked again at the next run.
- **Which files.** Uncompressed Blorbs (IFDB `blorb/…` format or a Blorb extension) of the formats in
  `PICTURE_FORMATS` (Glulx). Zipped Blorbs are not inspected (their head is the zip's); Z-code Blorbs join once an
  engine draws their pictures.
- **Report.** `report.json` has `counts.pictures: { blorbs, inspected, illustrated }`; the job summary shows them.
  `meta.json` has `illustrated`, checked against the rows by the emitter's validation.
- **Library.** The "Illustrated" filter is a single yes choice on the first page of the panel, under "Start here", shown
  only once the catalogue has illustrated games (like forgiveness); hash key `ill=1`.
- **Fixtures.** The parser's tests build Blorbs with `scripts/fixtures/build-blorb.ts` (which gained an optional `Fspc`
  chunk, at the head or at the end) and use the committed `picture.gblorb`, `lamp.ulx` and `media.ulx`. HTTP is
  replayed with `Response` objects. The sample catalogue reads `tests/fixtures/pictures.json`, in the cache's format,
  which makes the synthetic Glulx game "Bells of Aldermere" illustrated.
- **Not measured yet** (the development environment cannot reach the IF Archive): whether it honours `Range`, and how
  many catalogue games are illustrated. The first weekly run's job summary answers both (the "Illustrated games"
  section and `report.json`); that count decides the Home shelf follow-up. `Pict` entries that are placeholder `Rect`
  chunks (no image) count as pictures: telling them apart would need reading each resource's chunk header.
- Background: the brainstorm in [post-v1-ideas.md](../post-v1-ideas.md) found that illustrated Glulx games give
  static, detailed pictures that suit e-ink, with an engine and a catalogue V1 already has.
- To check at implementation: whether the IF Archive honours `Range` requests, and how many catalogue games turn out
  to be illustrated (this decides the Home shelf follow-up).
