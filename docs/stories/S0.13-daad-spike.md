## User story

As the product owner, I want to know whether an illustrated DAAD adventure can be played on the Kindle, which DAAD
games could be offered, and what jDAAD's GPL licence would mean, so that DAAD games can be decided on facts, before
any catalogue or engine work.

## Background

[post-v1-ideas.md](../post-v1-ideas.md#illustrated-retro-adventures) lists **DAAD** (the 1988 Aventuras AD system,
revived by DAAD Reborn, DAAD Ready and Adventuron's experimental DAAD export) as worth a look: parser adventures with
location pictures, which suit e-ink. Read from the code of [jDAAD](https://github.com/Utodev/jDAAD) (Uto, GPL-3,
last commit 2026-09-01, `versionDate` 24/06/2025):

- **Pure JS, small:** `jdaad.js` 152 KB raw, **32 KB gz**, plus jQuery 3.6 (~30 KB gz), `font.js` and `extern.js`
  (1 KB gz each).
- **Syntax above the baseline:** class fields (`class DDBHeader { version = 0; … }`, ES2022) and arrow functions. The
  Kindle runs ES2015–2017 only (SPEC §2.2), so the runtime must be transpiled (esbuild, target `es2017`).
- **Game data:** the DAAD Reborn Compiler's HTML target writes the database as a JS file (`daad.jddb`, a `DDBDATA`
  byte array, loaded by a `<script>`); pictures are PNG files per number (`images.js`, `jDAADImager`). A database
  built for another machine runs once its pointers are relocated (notes below).
- **Display:** a 320 × 200 canvas (with a double buffer); the **text is drawn into the canvas** with a 6 × 8 bitmap
  font (53 columns × 25 lines), pictures in windows above it; CSS scanlines on top. Scaled to the Kindle's 636 px,
  that is ~12 × 16 px per character.
- **Input:** a `keydown` handler, an HTML virtual keyboard shown when `'ontouchstart' in document.documentElement`,
  which is **false on the Kindle** although touch events fire (S0.3). Saves go to `localStorage` directly.
- **Licence:** GPL-3. Inkventure is MIT; a separate probe page shipping jDAAD unchanged with its licence and source
  is plain aggregation, but an engine bundled in the app is a decision for the owner.
- Games are few and scattered, many in Spanish; Adventuron games could become playable through its DAAD export.

## Scope

- A standalone page `public/probe/daad/` (no build dependency, like the Decker probe), with the pinned jDAAD (record
  commit and licence, fetched and SHA-256-checked like Decker and Quixe; `LICENSE` and a link to the source shipped
  next to it) and **one real illustrated game** built for jDAAD whose licence allows it (record the game, its author,
  its language and its licence). If none can be found in time, a tiny two-location game with one picture each,
  written by us with DAAD Ready / DRC, committed as its compiled output.
- **Patch the runtime** as small patches applied by a build script, each matching the pinned code exactly once (as
  for Decker), then transpiled to ES2017:
  - no scanlines, no transitions or delays beyond what the game asks; the canvas zoomed to the width without
    smoothing;
  - the virtual keyboard shown from touch support detected by an event (or a probe flag), not `ontouchstart`; its keys
    at least 48 px; and, as for Decker, a try with **the Kindle's own keyboard** through a hidden input;
  - any loop or timer that redraws while waiting for input stopped; saves left as they are (outside the app's storage,
    probe only).
- **Measure on the Kindle**, shown on the page and as QR codes (like the probes): transpiled runtime parse and start,
  first picture and text drawn, one command (typed or tapped to the answer drawn), a location change with a new
  picture; CPU idle while waiting for a command (no draw in 10 s); whether the bitmap text and the pictures read on
  e-ink (photos of the screen in the report).
- **Text in the reader instead of the canvas:** from the code, estimate what it would take to send jDAAD's text to
  Inkventure's paginated reader (window output, `ANYKEY` / `MORE` pauses, the input line) and only its pictures to a
  canvas or an image, as the Glulx pictures are; record it, do not build it.
- **Size:** patched runtime gz with and without jQuery, against the 100 KiB lazy-chunk budget (`size-budget.json`).
- **Catalogue reconnaissance**, recorded in the report, not built: DAAD games on IFDB (development system) and on the
  IF Archive, by language, those with a jDAAD (HTML) build, and whether a database from another target runs in jDAAD
  (try one); Adventuron's DAAD export (still experimental?).
- A report in `docs/device-reports/` and a recommendation in `post-v1-ideas.md` (go: a story for a DAAD engine and a
  catalogue, with the licence decision it needs; or no-go, and why). SPEC §13 updated with the answer.

## Acceptance criteria

- [x] The probe page plays the game in Chromium with the patches: the first location's picture and text are drawn, a
      command typed or tapped gets its answer, a move changes the picture, and nothing is drawn while the game waits.
- [x] A Kindle report recorded in `docs/device-reports/` with the measures above.
- [x] The catalogue count and the "text in the reader" estimate recorded.
- [x] A go / no-go recommendation in `post-v1-ideas.md`, with the GPL question for the owner, and SPEC §13 updated.

## Required tests

**Unit (Vitest)**

- The patch script applies to the pinned jDAAD and fails loudly if the upstream code it patches moved; the fetch
  script checks the files' SHA-256.

**E2E (Playwright)**

- The probe page loads the game, a command gets its answer (the canvas changes), and no draw happens while waiting
  for a command over a few seconds (counted by the patched runtime).

Plus the global gates: lint, size budgets (the probe is outside the app's budgets but its size is reported), CI green.
The transpiled runtime is ES2017 (which the Kindle's engine runs, SPEC §2.2): leave it out of `check:es5`, as for
Decker, and record why; the page's own script is still checked.

## Out of scope

- A DAAD engine in the reader, catalogue entries or the licence decision itself (after the go / no-go).
- Sound, original 8-bit snapshots (tape or disk images) and the other formats of `post-v1-ideas.md`.
- Bitsy ([S0.12](S0.12-bitsy-spike.md)).

## Notes & decisions

- **Pinned runtime:** jDAAD **1.2** (`versionDate` 24/06/2025), commit `053903d3` (2026-09-01, no tags), GPL-3, © Uto.
  `npm install` downloads `jdaad.js`, the `jquery-3.6.0.min.js` it ships (MIT), `font.js` (the DAAD 8 × 6 font) and
  `extern.js` into `vendor/daad/` and checks their SHA-256 (`scripts/build/daad-files.ts`, `fetch-daad.ts`), as for
  Decker and Bitsy. The licence is committed there and shipped next to the runtime (`/probe/daad/LICENSE-jdaad.txt`),
  and the page links to the source. DAAD Ready (commit `35849d04`) ships the same `jdaad.js` byte for byte; its
  `index.html` also loads `sounds.js` and `videos.js` (lists of the game's MP3 and MP4 files), which jDAAD's own
  `index.html` lacks: without them `PICTURE` on a number with no picture throws. The runtime defines both, empty.
- **Game:** no real game could be used: the 27 DAAD games on IFDB are commercial or freeware with no stated licence
  to redistribute, and the IF Archive has none (see the catalogue below). So, as the scope allows, **The Lamp Room**,
  written for the probe (`scripts/build/daad-game/lamp-room.dsf`, this repository's licence), from DAAD Ready's English
  template (`BLANK_EN.DSF`): two locations with a 320 × 96 picture each (a shore with a lighthouse, the lamp room),
  an object (matches), the keeper's log (a long text that pauses on *More…*), and an ending (`LIGHT LAMP` → `END`).
  Compiled with the **DAAD Reborn Compiler** (DRC commit `71df4e54`: frontend 0.40 built here with Free Pascal 3.2.2,
  backend 0.36 in PHP) for its HTML target: `public/probe/daad/lamp-room.jddb` (the DDB as a `DDBDATA` array). The
  frontend crashes when built with `-O2`; `fpc -g -gl` works. `scripts/build/daad-game/build.sh` rebuilds it.
- **Pictures are not PNG files** in jDAAD: DAAD Ready's `jDAADImager.php` turns each PNG into a JavaScript array of
  `0xRRGGBB` numbers (`images[n] = [pixel, …, x, y, width, height]`), drawn pixel by pixel. Ours are drawn by
  `scripts/build/daad-game/pictures.ts` and written in that format directly (a unit test rebuilds the committed
  `images.js` byte for byte): **571 KiB raw** for two pictures (5.4 KiB gz), which the device must parse.
- **Patches** (`scripts/build/daad-probe.ts`, each matching the pinned code exactly once, or the build fails naming
  it), then the whole runtime transpiled to ES2017 by esbuild (upstream uses class fields, ES2022):
  - **drawing:** upstream calls `fillRect` once per pixel, each with a colour string built from hex (30,720 calls for
    a picture, 48 per character). Every drawing now goes to an in-memory copy of each canvas (an `ImageData`), and
    the visible canvas gets only the rectangle that changed, once, when the interpreter stops to wait (a
    `setTimeout(0)` after the first change). jDAAD has **no loop or timer while it waits** (it returns from `run()`
    and waits for key events; timers only for a game's own `TIMEOUT`), so nothing is drawn while the game waits;
  - **no console log per condact** (`DEBUG_ENABLED` was on upstream: a styled `console.log` for every condact);
  - **zoom:** the canvas fills the width (or the height left by the keyboard), without smoothing; `?zoom=whole` for
    whole steps (×1 on a 636 px screen: 2 × 320 is 640). No scanlines (page markup, left out). Upstream's `DELAY`
    and `PAUSE` busy-wait as the game asks: kept;
  - **keyboard:** shown when the page says so, not from `'ontouchstart' in document.documentElement` (false on the
    Kindle although touch fires, S0.3); upstream's resizing of the screen and keyboard is gone (the page lays them
    out, keys 48 px high, ten a row); each key answers touch or mouse once (no `KeyboardEvent` built). A tap on the
    picture continues an `ANYKEY` or *More…* pause on every device (upstream: only without the virtual keyboard);
  - **the device's keyboard** through a text field under jDAAD's keys: a keydown with a real key is sent at once;
    where the device gives none (`Unidentified`), the field's text is compared with the last one and the difference
    sent as keys, Enter by the form's submit;
  - `?paper=white` (the default) swaps colours 0 and 15 so the text is black on white; `?paper=black` keeps the
    game's white on black;
  - saves stay in jDAAD's own `localStorage` keys (probe only); `window.ikDaad` exposes the measures.
- **Size (`check:size` reports it, not budgeted):** `runtime.js` **250 KiB raw, 60.3 KiB gz** as served
  (transpiled, not minified), of which jQuery ~35 KiB; **24.5 KiB gz without jQuery**. Minified with esbuild:
  **50.7 KiB gz** with jQuery, **19.3 KiB gz** without, a fifth of the 100 KiB lazy-chunk budget. jDAAD uses jQuery
  only for `ready`, event binding, `show`/`hide`/`css`: a few lines to replace in an engine.
- **`check:es5`:** `dist/probe/daad/runtime.js` is left out (`--not`), as for Decker: it is ES2017, which the
  Kindle's engine runs (SPEC §2.2). The page's `probe.js` and the game's `images.js` are ES5 and checked.
- **Chromium baseline** (headless, 636 × 740, this machine): runtime parse 4 ms, run 11 ms; first run (the intro, to
  its first wait) 4 ms, first draw 6 ms after the start; a command: its draw 2–15 ms after Enter (the whole screen,
  64,000 px, for a new location; the text window, 30,720 px, for an answer); a typed letter 0–1 ms (96–336 px);
  a picture 0–2 ms into memory; **10 s waiting: 0 draws**.
- **Text in the reader instead of the canvas** (estimated from the code, not built): all text goes through one
  function, `writeText` (then `writeWord`, `writeChar` into the bitmap), into one of 8 windows (`WINDOW`, `WINAT`,
  `WINSIZE`, `PRINTAT`, `TAB`, `CLS`, scroll), with pauses computed from the window's height (`getLastFittingChar`,
  *More…*, `#k`); input is `readText`/`readTextB` (the prompt and the echo drawn in the window), resumed through
  `getCommandB()`; pictures are `PICTURE` + `DISPLAY` into a window, or the GFX double buffer. An engine would:
  send the main text window's `writeText` to the reader's paginated text (and drop *More…*: the reader paginates),
  map `ANYKEY`/`INKEY` to a key chip, take the command bar's line into `inputBuffer` and call `getCommandB()`, send
  `DISPLAY` to an image in the transcript (the in-memory `ImageData` here, as Glulx pictures are), keep other windows
  (a status line drawn with `PRINTAT`) as an upper window (S1.15), and saves through `src/storage/`. About ten
  functions patched and an adapter like the Z-machine's: **one engine story, plus one for pictures and windows**.
  Hard cases: games that draw text into the picture (`PRINTAT` in window 0, the graphics charset `#g`), real-time
  `TIMEOUT`/`INKEY` games, and Spanish games' character table (`PatchStr`).
- **Catalogue reconnaissance** (2026-10-10, each IFDB page and the page it links to):
  - **IFDB: 27 games** with the DAAD system: 14 in English, 10 in Spanish, 3 in both. 11 are former commercial
    Aventuras AD titles (1988–1993), the rest 2005–2024 releases: freeware or "name your price", one commercial
    (Erinia). Illustrated: at least 7 (Maroland, Markham Manor's 128K/C64 builds, Colour Beyond Time's ESXDOS build,
    Erinia 2024, Rabenstein, El Cetro del Sol, Rudolphine Rur).
  - **With a jDAAD (HTML) build: 2**, both by Gareth Pitchford on 8bitag.com: *The Revenge of Moriarty* and *Dream
    Walker* (freeware, no licence stated). Others play in the browser through emulators (Spectrum, MSX, Atari ST via
    ADP) or as Adventuron or Twine remakes, not as DAAD databases. itch.io's `daad` tag has ~10 games, mostly emulator
    downloads, none saying it uses jDAAD.
  - **IF Archive: no DAAD game**; only `jdaadfc.py`, a font converter for jDAAD (MIT).
  - **Open licence: none found** (no CC, MIT, GPL or public domain game). "Freeware" does not grant redistribution;
    the DAAD binaries were put in the public domain by Andrés Samudio, but each game's database belongs to its author.
    A shelf needs each author's permission, game by game.
  - **Adventuron's DAAD export** is not called experimental any more, but is "provided without guarantee", "not
    guaranteed to work in all cases", supports graphics on the Spectrum Next and +3 only, and needs games written
    for it; users still report problems in 2025. It does not make Adventuron's catalogue playable.
  - **A database from another target in jDAAD** (DRC rebuilt at the same commit, The Lamp Room compiled for each
    machine): the **PC** database (VGA, EGA) is the HTML one but for the machine byte, and plays as it is. The
    **Spectrum** (v3, and classic v2 like the 1988 releases), the **MSX** and the **Atari ST** builds, wrapped as
    `DDBDATA`, **hang jDAAD** on load: the 8-bit machines' pointers include the load address (0x8400, 0x0100) and the
    ST writes words big-endian, while jDAAD reads every pointer as a little-endian offset from 0. Moving the 155
    pointers (13 in the header, the process tables and entries, the text and connection lookups) to 0 and writing them
    little-endian is enough: all four then play the whole walkthrough like the HTML build (the ST one is then the HTML
    one byte for byte, but for the machine byte). `scripts/build/daad-game/relocate.ts` does it; unit tests on the
    Spectrum v2 and ST builds (`tests/fixtures/daad/`), and an e2e test plays both relocated.
  - **What that does not cover:** an original release's database still has to be extracted from its tape or disk
    image, and its **pictures** are in each machine's own graphics database (DAAD's vector and bitmap formats), which
    jDAAD does not read: they would need a converter to jDAAD's picture arrays, machine by machine. So an original
    text-only game could play from its relocated database; an illustrated one needs that converter too.
- **Kindle run** (2026-10-10, PR #95 preview, [report](../device-reports/2026-10-10-kindle-daad.txt)), The Lamp Room
  played to the keeper's log:
  - **Start:** downloads ~1.7 s (runtime 250 KiB in 1 s, pictures 571 KiB in 0.4 s, game 19 KiB), then parses
    (pictures 47 ms, runtime 30 ms) and runs: the first screen **158 ms** after the start.
  - **Input:** a typed letter drawn in **2 ms** (96 px); a command answered in **194 ms** (READ LOG, a text window of
    30,720 px); a tap through *More…* 78 ms; each picture **129 ms** to draw into memory (the per-pixel arrays).
    That is the code's time: the e-ink repaint comes on top.
  - **Idle: 0 draws in 10 s** while the game waits for a command.
  - **Keyboards:** the Kindle's own keyboard sends real `keydown` keys to the text field (8 keys, none
    `Unidentified`, one submit), so typing works without the fallback; jDAAD's on-screen keys answered 98 touches.
    The screen is drawn at zoom 1.97 (630 px).
- **Recommendation: no-go for now, technically ready** (written in
  [post-v1-ideas.md](../post-v1-ideas.md#illustrated-retro-adventures), SPEC §13). jDAAD is as fast as Bitsy on the
  Kindle and smaller once minified without jQuery (19 KiB gz), and the Kindle keyboard works. What stops it is
  content: 27 DAAD games on IFDB, none under an open licence, 2 with a jDAAD build, none on the IF Archive; original
  releases would need extracting from tape or disk images and, for pictures, a converter per machine. It is worth
  reopening when authors agree to be on a shelf (first Gareth Pitchford's two jDAAD games, which have their pictures
  in jDAAD's format already) and the owner accepts jDAAD's GPL-3 in a lazy engine chunk. The engine story would
  then send the text to the reader (estimate above) and keep pictures as images. The decision is the owner's.
