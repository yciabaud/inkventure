## User story

As a reader, I want to keep an adventure on my e-reader and play it without Wi-Fi so that I can read on a train or
anywhere without a connection.

## Scope

Confirmed by the S0.9 device report ([2026-10-02](../device-reports/2026-10-02-kindle-offline.txt)): on the Kindle a
Service Worker serves the page with the network off, and the Cache API and IndexedDB both keep files across browser and
device restarts (quota 100 MB).

- **Offline app shell.**
  - A Service Worker at the app's scope precaches `index.html`, the JS and CSS bundles (modern and legacy), fonts
    and i18n.
  - It precaches the engine chunks of the formats of the kept adventures.
  - Its precache list is generated at build time. The cache is versioned per build; the old cache is dropped on
    activation.
  - App navigation is served from the cache first, so the app opens with Wi-Fi off. When online, a new build is
    picked up on the next launch.
- **"Keep offline" on an adventure.** In game detail and in the "⋯" menu of *My adventures*:
  - The story file is stored and pinned: never evicted by the LRU, unlike the cache of S3.4.
  - Its `games/<tuid>.json` and cover thumbnail are stored too.
  - Storage: the Cache API (it holds HTTP responses, which suits story files and covers, and the Service Worker
    can read it) through `src/storage/`. IndexedDB, also measured, is the alternative. localStorage is the fallback
    for files under 512 KB on browsers without either.
  - Starting a game keeps it offline automatically, within a size budget.
- **Offline state in the UI.**
  - Home works fully offline from local data.
  - Library and Featured show an "Offline: connect to browse the catalogue" page instead of failing.
  - Adventures that are not kept show "Needs Wi-Fi" and cannot be started.
- **Settings.** A list of kept adventures with their sizes and storage used, and "Remove from device". Sizes are
  counted by the app: the Kindle's `navigator.storage.estimate()` under-reports usage.
- i18n strings in `en.json` and `fr.json`.

- [x] A new deployment is picked up online without breaking a kept adventure.
- [x] Kept files are never evicted silently; removing one frees its space.

## Required tests

**Unit (Vitest)**

- Precache list generation from the build manifest.
- Kept-file store: pin, unpin, sizes, LRU leaves pinned files alone, fallback order.

**E2E (Playwright)**

- Chromium, same offline technique as S0.9: keep the fixture Z-machine game, go offline, reload; Home opens, the game
  plays and saves, and Library shows the offline page.
- Remove from device, then the game shows "Needs Wi-Fi" offline.

Plus the global gates: lint, `es-check es5` on the legacy bundle, size budgets (the Service Worker counts as initial
JS), CI green.

## Out of scope

- Offline catalogue browsing (Library shards and covers).
- Background sync of anything; saves are already local.

## Notes & decisions

- **Kindle check (2026-10-03, PR #77 preview):** every step of the checklist's section 7 passes, except the ebook's
  link, which points to the released app and so cannot be tried on a preview. Still to check after the release: does a
  link from the ebook (S6.2) reach the browser in airplane mode, or does the Kindle ask for Wi-Fi first? If it asks, the offline path is a browser bookmark, and the
  ebook and the app should say so. S0.9 only tested a bookmark.
- S0.9 also found that `navigator.storage.persist()` is refused on the Kindle: kept files could in theory be dropped
  under storage pressure. Nothing was lost in the probe's runs. If it happens, the game should show "Needs Wi-Fi" and
  offer to download it again, never fail.
- **Service Worker** (`src/sw/sw.js`, plain ES5 and checked by `es-check`, written to `dist/sw.js` by
  `scripts/build/service-worker.ts` with the precache list in place of its placeholder). The list comes from Vite's
  manifest: entries (modern, legacy, polyfills) with their imports and CSS, the fonts, and every lazy chunk that is not
  an engine (French dictionary, saves, story files, the kept-adventures page…) make the shell (~30 files); engine
  chunks are grouped by kind (`zmachine`, `glulx`, `ink`, `twine`). Fixture stories bundled for the demo are left out.
  The cache is `inkventure-app-<version>`, the version a hash of the list and the page (whose build meta tag changes
  with every build); the previous build's cache is deleted on activation, and its files with the same hashed name are
  copied rather than downloaded again.
- **Update: taken over at once, used from the next launch.** A waiting worker would wait for every tab to close,
  which a reload does not do and the Kindle rarely does, so the new worker calls `skipWaiting()` and `clients.claim()`.
  The page already running keeps its own build, but it would ask for lazy chunks of the previous build that the
  deployment removed (and its cache too): so after a `controllerchange` (when a worker was already in control) the
  page reloads at its next change of screen. Registration uses `updateViaCache: 'none'`; the page (`./`) is cached
  with `cache: 'no-cache'` so a stale HTTP copy is never kept.
- **Only the app's own requests are answered.** Navigations to the app's page and the build's files; nothing else
  (catalogue, covers, story files, the probe, the ebook page, PR previews under the same scope) is touched.
- **Kept files are read by the page, not through the worker.** `src/storage/keptFiles.ts` reads the Cache API
  (`inkventure-kept`) directly, so a kept adventure also plays before the worker controls the page, and the
  localStorage fallback works the same way. The kept list is `ik:v1:kept` in localStorage (synchronous: Home and the
  game page know at once what plays offline); `kept/index.json` in the kept cache lists the engines for the worker.
- **IndexedDB is not used** (the story allows it as the alternative): every browser with a Service Worker has the
  Cache API, and without a worker the app cannot open offline anyway. Fallback order: Cache API, then localStorage for
  stories under 512 KB (`ik:v1:kept:<tuid>`, not evictable: the LRU only evicts `file:` entries).
- **Deviation: covers are not kept.** IFDB's `coverart` sends no CORS headers (checked 2026-10-03), so a cover could
  only be stored as an opaque response, which Chromium pads to megabytes in the quota (and whose size the app cannot
  count). Offline, a kept game shows its typographic cover (the image fails to load). Follow-up if wanted: measure
  opaque padding on the Kindle, or have the catalogue pipeline mirror small thumbnails.
- **Auto-keep budget: 40 MB** (`AUTO_KEEP_BUDGET`) for all kept adventures together, under half the Kindle's 100 MB
  quota. A game started is kept 2 s after its start (like the story file cache) instead of being cached in
  localStorage; over the budget, or when the cache refuses it, it is cached as before. "Keep offline" has no budget;
  it also adds the game to My adventures (offline, Home is the only way to reach it).
- **Lost files** (`persist()` is refused): a kept game whose files are gone is downloaded again online; offline it
  says "This adventure's file is no longer on this device".
- **Offline is `navigator.onLine === false`** (the Kindle reports it in airplane mode, S0.9), plus a failed request
  when online. The Library and Featured fall back to "Offline: connect to browse the catalogue" only when offline;
  online failures keep their error pages.
- **Size budgets:** `sw.js` (2.7 KiB gz) counts as initial JS of the **modern** bundle only: a browser that needs the
  legacy bundle (no ES modules) has in practice no Service Worker. The legacy first load is at **199.9 / 200 KiB**
  (197.5 before): the Settings page of kept adventures is its own lazy chunk, and the keep logic is in the lazy
  `catalog/offline.ts`. The next story touching the initial bundle will need to make room.
- **E2E:** the app's worker is blocked in every test (`serviceWorkers: 'block'` in `playwright.config.ts`; it would
  answer requests before `page.route` sees them) and allowed in `offline.spec.ts` and the probe's test. Playwright
  cannot serve another `sw.js` to the browser's update check, so the "new deployment" test turns the current cache into
  a previous build's and unregisters the worker; the fresh install must rebuild the shell and the kept game's engine
  from `kept/index.json` and drop the old cache.
- **e2e in WebKit:** Playwright's WebKit contexts are private sessions, which drop an origin's Cache API entries as
  soon as none of its pages is open (a persistent WebKit profile keeps them, as the Kindle does). The tests that check
  a kept game after a new load open the app in a new page while a static page of the app stays open
  (`tests/e2e/helpers/session.ts`).
