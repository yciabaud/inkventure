## User story

As a player, I want to play Decker decks (HyperCard-like games of cards and buttons) in the reader, so that this
1-bit, tap-driven kind of game, made for screens like mine, is in Inkventure too.

## Background

The [S0.11 spike](S0.11-decker-spike.md) ran the tour deck on the Kindle with a patched web-decker
([report](../device-reports/2026-10-10-kindle-decker.txt)): ~8.5 s to open, **1.1–1.4 s** from a tap to the new card
(a tick ~450 ms, a draw ~550 ms), no CPU on a still card, and the device keyboard never opens on the canvas. The owner
decided **go** (2026-10-10), with the conditions of the [recommendation](../post-v1-ideas.md#decker): cut the draw,
remove the editor, type with the Kindle's keyboard, card-and-button decks first, under 1 s per tap.

## Scope

- **A Decker reader** like Twine's (S1.9): no `Engine`; the deck runs in `<iframe sandbox="allow-scripts" srcdoc>`
  (opaque origin, no access to the app) inside the usual reader chrome, as its own lazy chunk (`DeckerReader`).
  `engineFor('decker')`, `isAvailable` true on the modern bundle only: Decker is ES2017, so a device on the legacy
  bundle says the game cannot be played there.
- **The runtime**, built from the pinned Decker release by the S0.11 patch script, as an asset the frame loads:
  - the S0.11 patches: loop only while busy, draw only on change, no transitions, frozen animated patterns, steady
    cursor, full width, no corners;
  - **the editor removed** (menus, drawing tools, toolbars, object mode, script editor, property dialogs) and the
    sound code left out, so that it fits the 100 KiB gz lazy-chunk budget (two assets, the Lil interpreter and the UI,
    if one cannot; the budget is not raised);
  - **a faster draw:** convert and put only the rows of the frame buffer that changed (the patched `sync` already
    compares them), and measure what a tick spends to cut what can be cut.
- **Typing:** a tap on an editable field puts a hidden text input over it and focuses it, so that the device keyboard
  opens; what is typed, Backspace and Return go to the Decker field; Decker's drawn keyboard (`keycaps`) is off.
- **Saves:** a deck keeps its state in itself. When the deck goes idle after a change, the frame sends the deck
  (serialized as Decker saves it) to the reader, which keeps it under `save:<tuid>:decker` through `src/storage/`
  (debounced, at most a fixed size: a larger deck plays but does not resume, and the reader says so once). Opening the
  game resumes from it; **Restart** drops it. No Save / Restore / Undo / Transcript (as Twine).
- **Reader chrome:** the top zone shows the deck's name; menu: Aa (only what applies: nothing changes the deck's
  pixels), Restart, Refresh screen, Home / Library. A played deck joins My adventures (`lastPlayed`).
- **Fixture:** the tour deck (MIT, already downloaded for the probe) at `#/play/fixture-decker`.
- SPEC §4.1 (formats), §4.3 (sandbox, now Twine and Decker), §4.4 (saves) and §13 row 12 updated.

## Acceptance criteria

- [x] The tour deck plays in the reader: a tap on a button changes the card, a field takes typed text from the
      device keyboard, and nothing is drawn on a still card.
- [x] The deck resumes where it was after a reload; Restart starts it afresh.
- [x] No lazy chunk or runtime asset over 100 KiB gz; first load unchanged.
- [ ] On the Kindle: a card change under **1 s** from the tap to its first frame, and the deck open in under **5 s**
      (or the Notes give the measured times and what is left, for the owner to decide).
- [ ] Checked on the PR preview and on the Kindle.

## Required tests

**Unit (Vitest)**

- The patch script removes the editor and fails loudly if the upstream code it patches moved.
- The row-diff draw: only changed rows are converted (a frame buffer with one changed row).
- Deck save storage: size cap, Restart clears it.

**E2E (Playwright)**

- `#/play/fixture-decker`: the deck opens in the frame, a tap on a button changes the card, typing into a field
  through the hidden input changes the field, a reload resumes on the same card; the frame cannot reach the app
  (as the Twine sandbox test).

Plus the global gates: lint, `es-check es5` (the runtime asset left out, as in S0.11), size budgets, CI green.

## Out of scope

- Decker games in the catalogue: [S2.9](S2.9-decker-catalogue.md).
- Sound, Decker's `danger` JavaScript bridge (stays off), decks that draw or animate in real time.

## Notes & decisions

- **Reader:** `DeckerReader` (lazy, behind `LazyDeckerReader`) like Twine's: the deck's frame is
  `<iframe sandbox="allow-scripts" srcdoc>`, its page built by `src/engines/decker/deckerHtml.ts` with Decker's markup,
  the deck in its `<script language="decker">` block and the two runtime scripts **inlined**: an opaque-origin frame is
  not served by the app's Service Worker, so the reader fetches the scripts (through it, cached offline with the
  `decker` engine files of `sw.js`) and passes their text. `EngineKind` gains `decker`; `isAvailable('decker')` is
  false on the legacy bundle (`import.meta.env.LEGACY`), Decker being ES2017. Top zone: the deck's name (from the
  frame) and "Experimental"; menu: Restart (its own text: where the player was is lost) and Refresh screen.
  `ReaderFrame` gains `textSettings` (false here: "Aa" cannot change what the deck draws).
- **Runtime** (`scripts/build/decker-runtime.ts`, `virtual:decker-runtime`): the probe's patches (now named exports
  of `decker-probe.ts`; the probe's runtime is unchanged, byte for byte), then:
  - **draw:** upstream's `sync` replaced: the rows that changed since the last draw are found by comparing the frame
    buffer with the last one drawn, converted through a table (256 pixel values x the 64 positions of an 8 x 8 tile,
    rebuilt when the palette, the animated patterns or the colours change) into a `Uint32Array` view of the image, and
    only that strip is put on the canvases (one row more each side on screen, for a fractional zoom). Throttled
    Chromium (CPU / 20), tour deck, a card change: draw **2–35 ms instead of 91–150 ms** with the probe's runtime, the
    tap's first frame 132–271 ms instead of 217–317 ms. Ticks unchanged (the UI drawn into the frame buffer):
    cutting them would be a refactor of decker.js. On the Kindle, still to measure;
  - **keyboard:** `keycaps_enter` is a no-op. The bridge's hidden `<input>` (opacity 0, 16 px font) is placed under
    the tapped field and focused **in the `touchend` / `mouseup` handler**, where browsers allow the keyboard to open;
    which field was tapped is computed there from Decker's widgets (unlocked, shown fields under the point). Keys
    Decker knows reach the field through its own `keydown` handler (which cancels them); text a virtual keyboard sends
    as an `input` event is passed to `field_input`. Decker only enters the field at its next tick: a character typed
    before that stays in the input (its `keydown` is kept from Decker's handler, which would drop it) and is passed to
    the field at the next draw (seen in WebKit, where the test typed at once). The input is blurred when the field is
    left;
  - **bridge:** `ready`, `title`, `save` (a second after the deck goes idle following an input, only when the deck
    text changed) and `error`, posted to the parent with `ikDecker: 1`; the reader checks `event.source`.
- **Two scripts, editor kept (deviation from the owner's decision of S0.11):** the S0.11 note said the editor must
  be removed to fit the budget. Minified with esbuild, Decker splits into the Lil interpreter (**53.5 KiB gz**) and
  the UI (**60.4 KiB gz**), each under the 100 KiB lazy-chunk budget, which the story allows. Removing the editor is
  a refactor of decker.js: its sections (drawing tools, object mode, toolbars, script editor, sound editing, the
  listener) are called from the rest of the runtime (`bg_*`, `ob_*`, `n_play`, `sound_*`… are reached from scripts
  and modals), so cutting them safely means tracing every call. It would save bandwidth, not budget, and the parse
  time it would save is small (the whole runtime parsed in 58 ms on the Kindle). It stays unreachable (menus off).
  Left as a follow-up if the owner still wants it.
- **Saves:** `src/storage/decker.ts`: `save:<tuid>:decker` = `{v: 1, date, deck}`, at most `DECKER_MAX_CHARS`
  (1,000,000; a larger deck plays, does not resume, and the reader says so once), never evicted, removed with the
  game's saves. The deck as Decker writes it holds the current card, so a reload opens where the player was.
- **Fixture:** `#/play/fixture-decker`, the tour deck, emitted as an asset next to the runtime (the reader fetches
  it when no story is given).
- **Licences:** Decker joins `licences.txt` (vendored, like Quixe) and Settings → About.
- **Size check:** `assets/decker-(lil|ui)-*.js` are budgeted as lazy chunks (they are assets, not chunks).
- **Tests:** unit (`decker-runtime.test.ts`: each patch once, the scripts parse and fit, the row draw and its colours
  run against a stand-in of Decker's globals; `deckerHtml.test.ts`; `storage/decker.test.ts`) and e2e
  (`decker.spec.ts`: a button changes the card, a tap on a field focuses the hidden input, keys and an `input` event
  reach the field, the save, a reload on the same card with the same text, Restart, no draw on a still card, the
  frame cannot reach the app). Playwright's `serviceWorkers: 'block'` reads `navigator.serviceWorker` in every frame,
  which a sandboxed frame refuses with a page error: the test ignores that one.
