## User story

As the product owner, I want to know whether a Decker deck can be played on the Kindle with a patched runtime, so
that Decker games can be decided on facts, before any catalogue or engine work.

## Background

[post-v1-ideas.md](../post-v1-ideas.md) ranks **Decker** (John Earnest's HyperCard-like tool, MIT) as the most
promising new format: a pure-JS runtime (`js/lil.js` and `js/decker.js`, about 127 KB gz), a documented text format,
1-bit cards of 512 × 342 that fit the Kindle's 636 × 740 viewport at 1:1, and decks listed on IFDB as web games. Its
blockers on the Kindle are known only from reading the code: `sync()` recomputes every pixel on every
`requestAnimationFrame`, transitions, `sleep` and animated patterns assume 60 fps, and input uses mouse and touch
events.

## Scope

- A standalone page `public/probe/decker/` (no build dependency, like the device and offline probes), with a pinned
  web-decker release (record version and licence) and **one real deck** whose licence allows it (record the deck, its
  author and its licence; one written by us if none does).
- **Patch the runtime**, as small patches applied by a script and kept in the repo:
  - redraw only when the card or a widget changed (dirty flag), never on an idle frame;
  - transitions jump to their end; animated patterns are frozen; `sleep` and `sys.frame` keep working at a low rate;
  - the editor and its menus are hidden or left out, if that trims the runtime.
- **Measure on the Kindle**, shown on the page and as QR codes (like the probes): runtime parse and start time, first
  card drawn, a card change, a button script, a field typed into with the on-screen keyboard; CPU idle on a static
  card (no redraw in 10 s); whether `new ImageData(w, h)`, `{ passive: false }` listeners and touch events work.
- **Size:** the runtime's size gz, as patched, against the 100 KiB lazy-chunk budget (`size-budget.json`), and what
  would be needed to fit (trimming, or a budget discussion with the owner).
- A report in `docs/device-reports/` and a recommendation in `post-v1-ideas.md` (go: a story for a Decker engine and a
  curated shelf; or no-go, and why). SPEC §13 updated with the answer.

## Acceptance criteria

- [x] The probe page plays the deck in Chromium with the patches: cards change on taps, and no frame is drawn while
      nothing changes.
- [ ] A Kindle report recorded in `docs/device-reports/` with the measures above.
- [ ] A go / no-go recommendation in `post-v1-ideas.md`, and SPEC §13 updated.

## Required tests

**Unit (Vitest)**

- The patch script applies to the pinned release and fails loudly if the upstream code it patches moved.

**E2E (Playwright)**

- The probe page loads the deck, a tap on a button changes the card, and no redraw happens on an idle card over a few
  seconds (counted by the patched `sync`).

Plus the global gates: lint, size budgets (the probe is outside the app's budgets but its size is reported), CI green.
`check:es5` covers `dist/probe/**`, but Decker is ES2017 (which the Kindle's engine runs, SPEC §2.2): leave
`dist/probe/decker/` out of it and record why.

## Out of scope

- A Decker engine in the reader, catalogue entries or an itch.io scraper (after the go / no-go).
- Bitsy, DAAD and the other formats of `post-v1-ideas.md`.
- Sound.

## Notes & decisions

- **Pinned release:** Decker **v1.71** (tag `v1.71`, MIT, © John Earnest). `npm install` downloads `js/lil.js`,
  `js/danger.js` and `js/decker.js` into `vendor/decker/` and checks their SHA-256
  (`scripts/build/decker-files.ts`, `fetch-decker.ts`), as for Quixe. The licence is committed there and shipped
  next to the runtime (`/probe/decker/LICENSE-decker.txt`).
- **Deck:** `examples/decks/tour.deck` from the same tag: the guided tour web-decker opens by default, by John
  Earnest, under the repository's MIT licence. 24 cards, buttons with scripts (`go[...]` with transitions, `alert`),
  editable fields, sliders, grids and canvases. 112.6 KiB, 44 KiB gz.
- **Page:** `public/probe/decker/` (static `index.html` + ES5 `probe.js`, checked by `check:es5`) downloads the deck
  and `runtime.js` with XHR, then runs the runtime from a `<script>` element so that download, parse and start are
  timed separately. The deck is at the top at Decker's own integer zoom (1:1 on the Kindle), the live measures and a
  **Report & QR code** button below. The panel stops its taps from reaching Decker, whose `touchstart` handler on
  `<body>` cancels them.
- **Runtime:** `runtime.js` is built by `scripts/build/decker-probe.ts` (a Vite plugin; the dev server serves it too):
  what `scripts/web_decker.sh` puts in its `<script>` (`VERSION`, `DANGEROUS=0`, `lil.js`, `danger.js`, `decker.js`)
  with `decker.js` patched. Each patch must match the pinned code exactly once, or the build fails naming it:
  - **loop:** a tick (the whole UI drawn into the frame buffer) runs on an animation frame only while the deck is busy
    (a running script, `sleep`, a pending `view`, a held pointer, a frame that changed); after two quiet ticks the loop
    stops, and pointer, touch, wheel and key events start it again. One tick per frame, no catch-up: on a slow device
    the deck slows down instead of piling up ticks. So `sleep[n]` and `sys.frame` keep counting ticks, at whatever
    rate the device manages. Animated widgets keep it ticking at 4 Hz;
  - **sync:** draws only when the frame buffer or the palette changed since the last draw (upstream converts and puts
    all 175k pixels on every frame);
  - transitions jump to their end (no transition modal); animated patterns are frozen; the field cursor is steady;
  - menus are off as in a locked deck, so the editor cannot be reached. Its code is still in the runtime: trimming it
    is a refactor of `decker.js`, left to the engine story if the answer is go;
  - `window.ikDecker` exposes the measures (ticks, draws, durations, per-input times) to the page.
- **Input:** Decker's own mouse and touch handlers are unchanged (touch events, `{ passive: false }` on
  `touchstart`). The probe reports which features the device has and counts the events it sees.
- **Size (patched, `check:size` reports it, not budgeted):** `runtime.js` 416 KiB raw, **125 KiB gz** as served
  (unminified). Minified with terser: **107 KiB gz**, still over the 100 KiB lazy-chunk budget. Split as Decker
  already is, each part fits: `lil.js` 50 KiB gz and `decker.js` 56 KiB gz minified. Fitting would take either two
  lazy chunks (interpreter, then UI) or trimming the editor out of `decker.js`; either is for the owner to decide with
  the go / no-go, the budget is unchanged.
- **`check:es5`:** `dist/probe/decker/runtime.js` is left out (`--not`): Decker is ES2017 (`**`, trailing commas in
  calls), which the Kindle's engine runs (SPEC §2.2). The page's own `probe.js` is still checked.
- **Chromium baseline** (headless, 636 × 740, this machine): runtime parse 12 ms, start 82 ms, first card drawn
  128 ms after start (tick 31 ms, draw 15 ms); a tap to a new card: first frame 14 ms, idle after 38 ms; idle
  10 s: 0 ticks, 0 draws.
- **Still to do:** the Kindle run (steps in [device-reports/README.md](../device-reports/README.md#decker-probe-story-s011)),
  its report, then the go / no-go in `post-v1-ideas.md` and SPEC §13.
