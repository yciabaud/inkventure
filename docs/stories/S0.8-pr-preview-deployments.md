## User story

As the project owner, I want each pull request deployed to its own folder of the site so that I can try it on my
e-reader before merging.

## Scope

- Workflow building each same-repository PR and publishing it to `pr-preview/pr-<number>/`, with a comment on the PR
  giving the link; the preview is removed when the PR is closed.
- The production deployment of `main` moves to the `gh-pages` branch (root), leaving `pr-preview/` untouched.

## Acceptance criteria

- [x] Opening or pushing to a PR publishes `https://yciabaud.github.io/inkventure/pr-preview/pr-<n>/` and comments
      the link on the PR.
- [x] Closing the PR removes its folder.
- [x] `main` is still deployed at the site root only after CI passes, and deploying it keeps existing previews.

## Required tests

**Unit (Vitest)** — none (workflow only).

**E2E (Playwright)** — none new: `tests/e2e/deploy.spec.ts` already checks that the build works under any sub-path
(relative `base`), which is what serving from `pr-preview/pr-<n>/` relies on.

Plus the global gates: lint, `es-check es5` on the legacy bundle, CI green.

## Out of scope

- Previews for PRs from forks (their token is read-only).
- Isolating preview storage from production (see Notes).

## Notes & decisions

- **Why a branch**: the "GitHub Actions" Pages source serves a single deployment, so previews in sub-folders need the
  "Deploy from a branch" source. `gh-pages` holds `main`'s build at its root and previews under `pr-preview/`.
- **Production** (`deploy.yml`): same trigger and gates as before (after CI succeeds on a push to `main`, or manual;
  rebuilds the validated commit, re-runs `check:es5` and `check:size`), then pushes `dist/` to `gh-pages` with
  `JamesIves/github-pages-deploy-action@v4` and `clean-exclude: pr-preview/`. A `.nojekyll` file makes Pages serve
  the files as they are.
- **Previews** (`preview.yml`): on `pull_request` (opened, reopened, synchronize, closed), build (without the CI
  gates: previews are for manual testing, CI remains the merge gate) and deploy with
  `rossjrw/pr-preview-action@v1`, which posts a sticky comment with the URL and deletes the folder on close.
  `GITHUB_SHA` is set to the PR head so `version.json` / the build meta tag name the commit under review.
  One concurrency group per PR, cancelling superseded builds.
- **One-time setup**: after the first run of either workflow has created `gh-pages`, set **Settings → Pages → Build
  and deployment → Source: Deploy from a branch → `gh-pages` / `(root)`**. Until then the site keeps serving the
  last Actions deployment.
- **Shared storage**: previews live on the same origin as production (`yciabaud.github.io`), so they share
  `localStorage` (`ik:v1:*`). Fine while the schema is stable; a PR that changes the storage schema could alter
  production data on the same device. Follow-up if it becomes a problem: namespace keys by base path in
  `src/storage/`.
